# What are your project's goals for impact for the upcoming three months?

Over the next three months (July through September 2026), our goal is to turn the multi-platform foundation laid in Q2 into a validated, modernized SDK that is ready for the Q4 app-developer platform (.NET Wallet SDK, MAUI sample app), while keeping the backend SDK reliable for its existing production users.

**1. Ship the multi-platform package and close out Q2**
The multi-target work (net10.0 + net8.0 + netstandard2.1) merged at the end of Q2 (PR #195). The first order of business is shipping it to NuGet as the stable 16.0.0 release, which also carries Protocol 27, SEP-45, and the modernization work out of beta, and landing the last close-out PR (#198: matrices re-pinned to Horizon v27.0.0 / RPC v26.0.1 plus the completed `getLatestLedger` response model). Two more things belong in this release rather than after it: the two bugs already triaged for the quarter (#193, #197), so a release positioned as stable does not ship over known defects, and a decision on the System.Text.Json dependency floor for the older target frameworks (PR #201), because goal 2's design depends on the outcome and retrofitting a dependency change into a stable major is worse than deciding up front. Everything else this quarter builds on this release. Protocol 27's Mainnet vote is July 8; the SDK's CAP-71 support is already merged and KAT-verified, so integrators are protected on day one.

**2. Modernize the JSON layer**
The SDK carries 905 `[JsonPropertyName]` attributes and hand-written polymorphic converters for effects and operations. Migrating to `JsonNamingPolicy.SnakeCaseLower` deletes about 810 of those attributes; the remaining ~90 are genuine wire-format exceptions (Soroban RPC uses camelCase, Horizon's HAL envelope uses `_links`/`_embedded`, and a handful of fields have names that never followed snake_case) and stay behind, documented. Replacing the two polymorphic converters with `[JsonDerivedType]` was verified against real Horizon payloads and works, but only on System.Text.Json 9 or later, because Horizon does not put the `type_i` discriminator first in the payload; that is the dependency decision named in goal 1. The payoff is maintenance economics: every future response model, including the four SEP model sets in goal 3, gets authored without attributes and cannot carry a field-name typo. This work simplifies the `JsonSerializerContext` source-generation adoption planned for Q4 but does not gate it (source generation works with the attributes present). Deleting public converter classes breaks the binary API, so this ships as 17.0.0, the last release of the quarter.

**3. SEP parity where it unblocks the Wallet SDK**
Q4's .NET Wallet SDK mirrors the architecture of the Flutter wallet SDK, which wraps SEP-1, 6, 7, 9, 10, 12, 24, 30, and 38. The base SDK has six of those today; SEP-7 (URI scheme), SEP-12 (KYC API), SEP-30 (recovery), and SEP-38 (quotes) are the missing four. We implement them, each with unit tests and a per-SEP compatibility matrix in the format we established in Q2, taking the SDK from 6 to 10 implemented SEPs. The remaining peer-parity SEPs (47, 48, 53) are deliberately deferred to Q4 so the quarter stays realistically scoped; SEP-53 (Final as of June 2026, and not yet shipped by any peer SDK) is the first candidate to pull forward if capacity allows.

**4. Validate MAUI, the gate for Q4**
With the multi-target packages published, we validate the SDK on iOS and Android via .NET MAUI: crypto (libsodium), the HTTP/SSE stack, and linker trimming. The first week of July includes a short desk check of the one risk we already know is concrete: neither NSec nor Sodium.Core ships iOS/Android native libsodium binaries in its standard runtime packages, so the fallback choice (build libsodium for those targets, or a managed Ed25519 path) gets decided before dependent work starts. Validation runs Release builds with trimming enabled, on iOS simulator and Android emulator plus at least one physical Android device; we add an iOS device smoke test if the provisioning set up in this deliverable allows it, and if it does not, the compatibility report states plainly that physical-iOS behavior (where AOT is enforced and there is no JIT) remains unvalidated risk carried into Q4. This includes standing up the MAUI development and test environment itself (Xcode + iOS simulators, Android SDK + emulators, MAUI workloads, signing/provisioning), planned as its own work item from prior MAUI experience. This is a validation milestone, not a sample app (that is Q4, together with the Wallet SDK).

# Please list the deliverables you aim to create in the next three months and explain their ecosystem value.

### Deliverable 1 — Ship Multi-Target to NuGet + Q2 Close-Out + Stable 16.0.0

- **Specific:** Ship the stable 16.0.0 release: the multi-target packages merged at Q2 close (PR #195, net10.0 + net8.0 + netstandard2.1 for both `StellarDotnetSdk` and `StellarDotnetSdk.Xdr`), Protocol 27 CAP-71, SEP-45, and the modernization work, all currently on `main` but published only as 16.0.0-beta. Land the last close-out PR (#198: matrices re-pinned to Horizon v27.0.0 / RPC v26.0.1 and the `getLatestLedger` response fields `closeTime`/`headerXdr`/`metadataXdr`). Settle the System.Text.Json dependency floor for net8.0/netstandard2.1 (PR #201) before tagging, since Deliverable 2's design depends on the outcome. Fix the two triaged bugs in 16.0.0 or a 16.0.1 within days of it: #193 (Horizon pagination drops auth/resilience configuration; the reporter has a fix ready for review) and #197 (RPC error responses not surfaced on `SorobanRpcResponse<T>`). Validate the published packages on all three targets (NuGet package validation, a netstandard2.1 consumer smoke test) and close tracking issues #159, #186, #188. Track the Protocol 27 Mainnet vote (July 8) for any post-vote follow-ups.
- **Measurable:** 16.0.0 stable on NuGet with three TFMs and passing package validation; PR #198 merged; the PR #201 decision recorded; #193 and #197 closed; the three tracking issues closed.
- **Achievable:** The feature code is merged; remaining work is close-out review, two scoped bug fixes (one with a fix already written by the reporter), release mechanics, and post-release fallout handling.
- **Relevant:** MAUI validation this quarter and everything in Q4 (Wallet SDK, Unity, Tizen) depends on the multi-target package being on NuGet, and the two bugs bite today's users of authenticated Horizon providers and Soroban RPC.
- **Time-bound:** First half of July, ahead of all dependent work.

### Deliverable 2 — JSON Modernization (ships as 17.0.0)

- **Specific:** Migrate response deserialization to `JsonNamingPolicy.SnakeCaseLower`, removing ~810 of the 905 `[JsonPropertyName]` attributes and keeping a documented exception list of ~90 (camelCase Soroban RPC fields, HAL `_links`/`_embedded`, legacy field names). Replace the hand-written `EffectResponseJsonConverter` and `OperationResponseJsonConverter` polymorphic converters with `[JsonDerivedType]`; this requires the System.Text.Json 9+ floor decided in Deliverable 1, and if that decision goes the other way, the converters stay and this deliverable is rescoped to the naming-policy migration alone. Replace `SendTransactionStatusEnumJsonConverter` with `JsonStringEnumMemberNameAttribute`; `LiquidityPoolTypeEnumJsonConverter` stays, because its enum lives in xdrgen-generated code that regeneration would overwrite. Entry criterion: the strict-JSON guardrails (duplicate-property rejection, nullability enforcement) are in place on net8.0/netstandard2.1 (PR #201), not only on net10.0 as today. Consumer-observable behavior changes (exception types on unknown discriminators, `type_i` serialization) are documented in the release notes.
- **Measurable:** `grep -r "JsonPropertyName(" StellarDotnetSdk/ | wc -l` drops from 905 to the documented exception list (~90 entries, committed alongside the migration notes); the two polymorphic converter files and one enum converter file are deleted; the full unit suite (about 1,930 test cases per target framework) and the live-Testnet integration suite pass on all TFMs, with a manually dispatched integration run on the branch before merge (the integration workflow otherwise runs only after merge).
- **Achievable:** Verified by spike work rather than assumption: 813 of the 905 attributes match the naming policy exactly when run through the real `SnakeCaseLower` implementation, and `[JsonDerivedType]` was tested against Horizon-shaped payloads with out-of-order discriminators on System.Text.Json 9 (it fails on 8, which is why the floor decision comes first).
- **Relevant:** Deletes ~800 lines of error-prone annotation surface and means every future response model, including this quarter's four SEP model sets, is authored attribute-free and cannot carry a field-name typo. It also simplifies, though it does not gate, the Q4 `JsonSerializerContext` source-generation work. Deleting public converter classes is a binary breaking change, hence the 17.0.0 slot.
- **Time-bound:** September, sequenced after the SEP minors so a regression here cannot block additive SEP releases.

### Deliverable 3 — SEP Expansion: SEP-7, SEP-12, SEP-30, SEP-38 (+ matrices)

- **Specific:** Implement the four SEPs the Wallet SDK needs for peer parity: SEP-7 (URI scheme for delegated signing), SEP-12 (KYC API), SEP-30 (multi-server account recovery), SEP-38 (anchor RFQ/quotes), each with unit tests and a per-SEP compatibility matrix in `StellarDotnetSdk/Compatibility/sep/`, following the 100%-field-coverage format established in Q2.
- **Measurable:** 4 new SEP namespaces with passing unit tests; SEP matrix count grows from 6 to 10; SDK goes from 6 to 10 implemented SEPs.
- **Achievable:** All four have reference implementations in the Flutter and iOS SDKs; SEP-12 and SEP-38 build on the SEP-10/45 WebAuth infrastructure already in the SDK, and the matrix format is established practice from Q2.
- **Relevant:** These four close the gap between the base SDK and the Flutter wallet SDK architecture that Q4's .NET Wallet SDK mirrors; they also close the largest remaining SEP-parity gap versus peer SDKs. SEP-30's ecosystem adoption is thin today, but every peer wallet SDK ships it and it is the recovery mechanism for the no-seed-phrase wallet UX the Q4 work targets. SEP-47/48/53 are deliberately deferred to Q4 to keep this quarter realistically scoped (SEP-53, Final since 2026-06-18 and unshipped by peers, is the first pull-forward candidate if capacity allows).
- **Time-bound:** Complete by end of the 3-month period.

### Deliverable 4 — MAUI Validation (incl. environment setup)

- **Specific:** Three parts. **Part 0, desk check (week 1 of July):** confirm whether the crypto backends (NSec, Sodium.Core) load on iOS/Android at all, given that neither ships native libsodium for those targets in its standard runtime packages, and pick the fallback (build libsodium for ios-arm64 and the Android ABIs, or a managed Ed25519 path) so the decision lands before dependent work starts. **Part A, environment:** stand up a reproducible MAUI development and test environment (macOS host with Xcode and iOS simulators, Android SDK with emulator images, .NET MAUI workloads, signing/provisioning configuration), documented with pinned workload and Xcode versions so it can be rebuilt directly for Q4's sample-app work. **Part B, validation:** validate the multi-target SDK via a minimal .NET MAUI validation app, built in Release with trimming enabled: Ed25519 crypto (native library loading), HTTP/SSE stack behavior, and linker/trimming compatibility, on iOS simulator, Android emulator, and at least one physical Android device, plus an iOS device smoke test if provisioning allows. Produce a documented compatibility report with any required workarounds (e.g. linker descriptors). If physical iOS is not exercised, the report says so explicitly, because iOS devices enforce AOT with no JIT and a green simulator run does not cover that condition.
- **Measurable:** Desk-check decision recorded in week 1; environment setup documented and reproducible; validation app builds and runs core SDK flows (keypair generation/signing, Horizon query, transaction submit, Soroban simulate) on the platforms listed above; findings and any residual unvalidated risk documented in-repo.
- **Achievable:** Scoped strictly to validation, not a product sample; the crypto abstraction from PR #195 was designed for exactly this portability. Environment setup is planned as its own work item from prior MAUI experience, not overhead absorbed elsewhere.
- **Relevant:** MAUI is the gate for Q4's Wallet SDK sample app. Discovering platform blockers now, not mid-Q4, is the point, and the native-crypto question is the single most likely blocker, which is why it moves to week 1. This is the quarter's highest-uncertainty item, which the capacity buffer is sized for.
- **Time-bound:** Desk check in week 1 of July; environment and validation in the second half of the quarter, after Deliverable 1 publishes the multi-target package.
