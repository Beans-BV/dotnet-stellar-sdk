# What are your project's goals for impact for the upcoming three months?

Over the next three months (July–September 2026), our goal is to turn the multi-platform foundation laid in Q2 into a validated, modernized SDK that is ready for the Q4 app-developer platform (.NET Wallet SDK, MAUI sample app), while keeping the backend SDK reliable for its existing production users.

**1. Ship the multi-platform package and close out Q2**
The multi-target work (net10.0 + net8.0 + netstandard2.1) is fully built with green CI and sits in final review as PR #195. Landing it and shipping the stable 16.0.0 release (which carries Protocol 27, SEP-45, the modernization work, and the Protocol 26 close-out — matrices re-pinned to Horizon v27.0.0 / RPC v26.0.1 and the completed `getLatestLedger` response model — out of beta) is the first order of business: everything else this quarter builds on it. Protocol 27's Mainnet vote is July 8; the SDK's CAP-71 support is already merged and KAT-verified, so integrators are protected on day one.

**2. Modernize the JSON layer — removing ~900 hand-written attributes**
The SDK carries 905 `[JsonPropertyName]` attributes and hand-written polymorphic converters for effects and operations. Migrating to `JsonNamingPolicy.SnakeCaseLower`, `[JsonDerivedType]`, and `JsonStringEnumMemberNameAttribute` deletes that maintenance surface, eliminates a whole class of field-name typo bugs, and is the prerequisite for source-generated (Native AOT-ready) serialization in Q4.

**3. SEP parity where it unblocks the Wallet SDK**
Q4's .NET Wallet SDK needs SEP-7 (URI scheme), SEP-12 (KYC API), SEP-30 (recovery), and SEP-38 (quotes) in the base SDK. We implement these four — each with unit tests and a per-SEP compatibility matrix in the format we established in Q2 — taking the SDK from 6 to 10 implemented SEPs. The remaining peer-parity SEPs (47, 48, 53) are deliberately deferred to Q4 so the quarter stays within budget; SEP-53 (now Final as of June 2026, and not yet shipped by any peer SDK) is the first candidate to pull forward if the capacity buffer goes unused.

**4. Validate MAUI — the gate for Q4**
With netstandard2.1/net10.0 packages published, we validate the SDK on iOS simulator and Android emulator via .NET MAUI: crypto (libsodium), HTTP stack, and linker trimming. This is a validation milestone, not a sample app (that is Q4, together with the Wallet SDK). Its outcome de-risks the entire Q4 plan.

**5. One fewer third-party dependency**
Replacing LaunchDarkly.EventSource with the built-in .NET `SseParser` on modern targets removes a third-party dependency from the streaming path.

A note on estimation: all effort figures below assume conventional hand-written development (AI assistance limited to code completion), and the quarter is capped at the same 200-hour budget as previous quarters — including recurring maintenance work and an explicit contingency buffer sized for the platform-validation risk this quarter carries.

### Deliverable 2 — JSON Modernization

- **Specific:** Migrate response deserialization to `JsonNamingPolicy.SnakeCaseLower`, removing the 905 `[JsonPropertyName]` attributes (keeping explicit exceptions where Horizon field names don't follow snake_case); replace the hand-written `EffectResponseJsonConverter` and `OperationResponseJsonConverter` polymorphic converters with `[JsonDerivedType]`; replace the custom enum converters (`LiquidityPoolTypeEnumJsonConverter`, `SendTransactionStatusEnumJsonConverter`) with `JsonStringEnumMemberNameAttribute`. Full regression validation against the existing 1,926-test unit suite and the live-Testnet integration suite.
- **Measurable:** `grep -r "JsonPropertyName(" StellarDotnetSdk/ | wc -l` drops from 905 to a small documented exception list; the two polymorphic converter files and two enum converter files are deleted; all unit + integration tests pass.
- **Achievable:** The strict-JSON guardrails shipped in Q2 (`AllowDuplicateProperties=false`, `RespectNullableAnnotations`, frozen options) catch regressions early, and the integration suite validates against real Horizon/RPC responses — the main risk of a rename-based migration.
- **Relevant:** Deletes ~900 lines of error-prone annotation surface, prevents field-name drift bugs, and is the precondition for `JsonSerializerContext` source generation (Q4, Native AOT).
- **Time-bound:** Complete by end of the 3-month period.

### Deliverable 3 — SEP Expansion: SEP-7, SEP-12, SEP-30, SEP-38 (+ matrices)

- **Specific:** Implement the four Wallet-SDK-prerequisite SEPs — SEP-7 (URI scheme for delegated signing), SEP-12 (KYC API), SEP-30 (multi-server account recovery), SEP-38 (anchor RFQ/quotes) — each with unit tests and a per-SEP compatibility matrix in `StellarDotnetSdk/Compatibility/sep/`, following the 100%-field-coverage format established in Q2.
- **Measurable:** 4 new SEP namespaces with passing unit tests; SEP matrix count grows from 6 to 10; SDK goes from 6 to 10 implemented SEPs.
- **Achievable:** All four have reference implementations in the Flutter and iOS SDKs; SEP-12 and SEP-38 build on the SEP-10/45 WebAuth infrastructure already in the SDK.
- **Relevant:** These four are hard prerequisites for the Q4 .NET Wallet SDK; they also close the largest remaining SEP-parity gap versus peer SDKs. SEP-47/48/53 are deliberately deferred to Q4 to keep this quarter inside budget (SEP-53, Final since 2026-06-18 and unshipped by peers, is the first buffer-overflow pull-forward candidate).
- **Time-bound:** Complete by end of the 3-month period.

### Deliverable 4 — MAUI Validation

- **Specific:** Validate the multi-target SDK on iOS simulator and Android emulator via a minimal .NET MAUI validation app: Ed25519 crypto (libsodium native library loading), HTTP/SSE stack behavior, and linker/trimming compatibility. Produce a documented compatibility report with any required workarounds (e.g. linker descriptors).
- **Measurable:** Validation app builds and runs core SDK flows (keypair generation/signing, Horizon query, transaction submit, Soroban simulate) on both platforms; findings documented in-repo.
- **Achievable:** Scoped strictly to validation, not a product sample; the crypto abstraction from PR #195 was designed for exactly this portability.
- **Relevant:** MAUI is the gate for Q4's Wallet SDK sample app — discovering platform blockers now, not mid-Q4, is the point. This is also the quarter's highest-uncertainty item, which the capacity buffer is sized for.
- **Time-bound:** Second half of the quarter, after Deliverable 1 publishes the multi-target package.

### Deliverable 5 — SseParser Migration

- **Specific:** Replace the LaunchDarkly.EventSource dependency (v3.3.2) with the built-in .NET `System.Net.ServerSentEvents.SseParser` on the net8.0/net10.0 targets (netstandard2.1 keeps the existing implementation), preserving the public streaming API and reconnect semantics.
- **Measurable:** LaunchDarkly.EventSource removed from the modern-target dependency graph; existing SSE unit tests plus the live `SseStreamingTests` integration test pass unchanged.
- **Achievable:** The SDK's streaming surface is already abstracted behind request builders; the integration suite provides live verification of event parsing.
- **Relevant:** One fewer third-party dependency in the supply chain of a financial SDK, and smaller deployment footprint on mobile targets.
- **Time-bound:** After Deliverable 1 (the TFM-conditional packaging it depends on).
