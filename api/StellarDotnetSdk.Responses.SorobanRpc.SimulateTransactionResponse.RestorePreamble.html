It can only present on successful simulation (i.e. no error) of InvokeHostFunction operations. If present, it indicates the simulation detected expired ledger entries which requires restoring with the submission of a RestoreFootprint operation before submitting the InvokeHostFunction operation. The MinResourceFee and SorobanTransactionData fields should be used to construct the transaction containing the RestoreFootprint operation.

MinResourceFee

Recommended minimum resource fee to add when submitting the RestoreFootprint operation. This fee is to be added on top of the Stellar network fee.

[JsonRequired]
[JsonNumberHandling(JsonNumberHandling.AllowReadingFromString)]
public required long MinResourceFee { get; init; }

Property Value

long

Remarks

JsonRequiredAttribute stops a preamble that omits the field entirely from reading as a free restore. This is a value type, so nothing else enforces presence: an object with no minResourceFee silently yielded 0, and a caller following the documented "use MinResourceFee and SorobanTransactionData to submit a RestoreFootprint operation" flow would then submit it underfunded. Stellar RPC declares the field json:"minResourceFee,string" with no omitempty, so a conforming server always sends it and requiring it rejects nothing.

This enforces presence only, not plausibility: an explicit "0" or a negative "-500" both satisfy the attribute and still describe a restore this SDK would submit underfunded. Nothing here range-checks the value, and SorobanTransactionData — the other half of the documented flow — carries no presence requirement at all, so a preamble consisting of nothing but a fee still deserializes. That matches the wire contract rather than a guarantee: Stellar RPC tags it json:"transactionData,omitempty" and sends transactionDataJson in its place when a request asks for JSON-format XDR. This SDK never asks for that, so a server replying to it includes transactionData in every preamble; the field is left optional to match the upstream contract and the top-level transactionData, not because a reply to this SDK can lack it. Callers who act on a preamble should check both fields rather than assume deserialization vouched for them.

required carries the guarantee to the other entry point, for the reason given on Type: the attribute binds only the deserializer, so without it new RestorePreamble() still produced the silent 0 this remark opens by describing.

The ,string in the tag quoted above is not decoration: the value arrives as a JSON string, and the SDK read it only because DefaultOptions sets AllowReadingFromString globally. This is a public type with public init accessors, so a caller whose own options bind the wire name but not the number handling got a JsonException on a conforming reply — independently of required, which governs an absent field rather than a string-shaped one. JsonNumberHandlingAttribute records the wire form here so it no longer depends on the ambient option; see the remarks on MinResourceFee for its effect on the write direction. It relaxes the read — a bare number still reads — so nothing that deserialized before is rejected.
