MinResourceFee

(Optional) Not present in case of error.

Recommended minimum resource fee (in stroops) to add when submitting the transaction. This fee is to be added on top of the Stellar network fee.

Stellar RPC declares this field as an int64, so it is modelled as a long: values above MaxValue (~429 XLM) are reachable on large uploads and restores.

See https://developers.stellar.org/docs/encyclopedia/fees-surge-pricing-fee-strategies#network-fees-on-stellar.

[JsonNumberHandling(JsonNumberHandling.AllowReadingFromString)]
public long? MinResourceFee { get; init; }

Property Value

long?

Remarks

Stellar RPC tags the field json:"minResourceFee,string,omitempty", so when present it arrives as a JSON string rather than a number. JsonNumberHandlingAttribute records that at the declaration instead of leaving it to DefaultOptions's ambient AllowReadingFromString. This is a public response type with public init accessors, so a caller can deserialize it with their own options — and one whose options bind the wire name but not the number handling (for example PropertyNameCaseInsensitive or a camelCase naming policy) got a JsonException on a conforming reply. Options that already imply AllowReadingFromString, such as Web, were never affected.

This relaxes the read rather than constraining it: the property now accepts a JSON string or a bare number, so nothing that deserialized before is rejected. It is not the read-side analogue of JsonRequiredAttribute, which rejects an absent field.

A property-level number-handling attribute replaces the ambient setting in both directions, so it also fixes the write shape: this property is always written as a bare number, even for a caller whose options set WriteAsString, and such a caller can no longer opt these two properties into Strict reads. That is accepted deliberately — the alternative, adding WriteAsString here, would change the serialized shape for every caller rather than for the few who configure that flag.

LedgerEntryChange[]

Remarks

A null element is rejected. RespectNullableAnnotations constrains the array reference, never its contents, so "stateChanges":[null] otherwise produced an array whose element was null despite the non-nullable element type — and the very loop Type's JsonRequiredAttribute was added to protect, foreach (var c in StateChanges) if (c.Type == "created"), then threw NullReferenceException instead of the JsonException every other malformed-payload path here reports.

The two entry points report differently, because they are different kinds of failure: a malformed payload is a JsonException raised by NonNullElementArrayJsonConverter<T> before the value is assigned, while passing a null element from ordinary C# is a rejected argument and raises ArgumentException — matching the convention the SDK's request types follow, and keeping a caller's catch (JsonException) from swallowing a programming error.

This is a check at assignment, not a maintained invariant: the array is stored and returned by reference rather than copied, so anything still holding the array can write a null back into it afterwards. It guards what arrives from the wire, which is where a null element actually comes from.
