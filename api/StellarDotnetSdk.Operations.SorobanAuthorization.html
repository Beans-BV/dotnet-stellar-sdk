Remarks

The credential address is taken from entry (matching the Java and JS SDKs); signer only supplies the signature. Signing with a key that does not correspond to the entry's address yields an entry the on-chain __check_auth rejects.

Entries carrying SorobanAddressCredentialsWithDelegates credentials keep their credential type (version is ignored): the payload is the CAP-0071-01 root-bound preimage shared by the top-level account and every delegate, the root expiration is updated to validUntilLedgerSeq, and the signatures of all non-target nodes are preserved — mirroring the JS SDK's authorizeEntry(..., forAddress). Throws ArgumentException when forAddress matches no credential node.

IMPORTANT — multi-party coordination: the signing payload embeds validUntilLedgerSeq, and this method updates the root credential's expiration to that value while leaving the other nodes' signatures untouched. Every party signing the same delegated entry must therefore pass the same validUntilLedgerSeq: re-signing with a different value invalidates the signatures already attached, because their payloads embedded the old expiration. As a partial safety net this method throws an InvalidOperationException when the expiration would change out from under an existing real (non-placeholder) signature it must preserve — both when signing a delegate while the root already holds a signature over a different expiration, and when re-signing the root (whether forAddress is omitted or names the root address) while a delegate already holds one. Delegate-vs-delegate mismatches (re-signing one delegate while a sibling is signed over a different expiration) cannot be detected here, because a delegate node carries no expiration of its own; fix the expiration once (e.g. via BuildWithDelegatesEntry(SorobanAuthorizationEntry, IReadOnlyList<ScAddress>, uint)) before collecting signatures.

AuthorizeEntryWithDelegates(SorobanAuthorizationEntry, ISorobanEntrySigner, IReadOnlyList<ISorobanEntrySigner>, uint, Network)

Signs an authorization entry as delegated credentials (Protocol 27, CAP-0071-01): the root signer authorizes, and each delegate co-signs on its behalf. Produces SorobanAddressCredentialsWithDelegates.

public static SorobanAuthorizationEntry AuthorizeEntryWithDelegates(SorobanAuthorizationEntry entry, ISorobanEntrySigner rootSigner, IReadOnlyList<ISorobanEntrySigner> delegateSigners, uint validUntilLedgerSeq, Network network)

Parameters

entry SorobanAuthorizationEntry

The entry to sign. Its credentials must be ADDRESS or ADDRESS_V2; source-account and already-delegated entries are rejected.

rootSigner ISorobanEntrySigner

The root account delegating its authorization.

The delegates co-signing on the root's behalf; input order is irrelevant, as the method sorts them into the protocol-required ascending-address order. May be empty, producing delegated credentials with no delegates.

The ledger sequence number on which the signatures expire.

The network the transaction is submitted to.

Returns

SorobanAuthorizationEntry

A new signed SorobanAuthorizationEntry with delegated credentials.

Remarks

Per CAP-0071-01, the top-level account and every delegate sign the same payload: the address-bound preimage (ENVELOPE_TYPE_SOROBAN_AUTHORIZATION_WITH_ADDRESS) bound to the top-level account's address. This method emits leaf delegates only (no nested delegates); to build deeper delegation chains, construct SorobanDelegateSignature values manually — every nested array must also be sorted by increasing address with no duplicates. The shared signing payload is cross-checked against the JS reference SDK by an in-repo known-answer test; the full delegated-entry XDR layout is locked by the vendored Protocol 27 schema.

The root credential address is taken from the entry; the root signer only supplies the root signature. Delegates are emitted sorted by increasing address as required by CAP-71; passing two signers with the same address throws an ArgumentException before any signer is invoked, because the protocol rejects duplicate delegate addresses at invocation time.

Exceptions

ArgumentNullException

Thrown when entry, rootSigner, delegateSigners, or network is null.

ArgumentException

Thrown — before any signer is invoked — when entry does not carry ADDRESS or ADDRESS_V2 credentials (source-account or already-delegated), when any element of delegateSigners is null, or when two delegate signers share the same address (CAP-0071-01 forbids duplicate delegate addresses).

BuildAuthorizationEntryPreimageHash(SorobanAuthorizationEntry, uint, Network)

Builds and SHA-256-hashes the signing payload for entry, selecting the preimage variant by the entry's credential type (the single source of truth, mirroring the JS SDK's buildAuthorizationEntryPreimage): V1 address credentials select the legacy ENVELOPE_TYPE_SOROBAN_AUTHORIZATION preimage; V2 and delegated credentials select the address-bound ENVELOPE_TYPE_SOROBAN_AUTHORIZATION_WITH_ADDRESS preimage bound to the (root) credential address. Use this to obtain the exact payload for external signers (e.g. hardware wallets) without going through AuthorizeEntry(SorobanAuthorizationEntry, ISorobanEntrySigner, uint, Network, SorobanCredentialsVersion, ScAddress?) .

entry SorobanAuthorizationEntry

The (typically simulation-produced) entry to convert. Its ADDRESS or ADDRESS_V2 credentials supply the root address and nonce. An entry that already carries delegated (WITH_DELEGATES) credentials is rejected with an ArgumentException (matching the JS SDK), because rebuilding it would discard every signature already collected on the existing delegate tree; sign such an entry incrementally with AuthorizeEntry(SorobanAuthorizationEntry, ISorobanEntrySigner, uint, Network, SorobanCredentialsVersion, ScAddress?) instead.

delegateAddresses IReadOnlyList<ScAddress>

The delegate addresses, one leaf node each; input order is irrelevant, as the method sorts them into the protocol-required ascending-address order. Duplicate addresses throw an ArgumentException. For deeper delegation chains, construct SorobanDelegateSignature values manually.

The ledger sequence number on which the signatures will expire. This value is embedded in every party's signing payload — fix it here once, and have every subsequent AuthorizeEntry call pass the same value.
