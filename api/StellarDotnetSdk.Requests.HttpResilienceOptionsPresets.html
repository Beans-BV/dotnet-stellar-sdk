ForHorizon()

Creates options tuned for the Stellar Horizon API. Retries connection failures and the transient HTTP status codes (408/429/500/502/503/504 — emitted directly by Horizon for rate-limit, timeout, ingestion, and overload cases, plus 408/502 from the CDN/LB layer fronting Stellar Foundation endpoints) on Horizon's GET queries and POST SubmitTransaction(). Up to 3 retries with exponential backoff (200ms-5s) and jitter; honors the Retry-After header (which Horizon sends on 429).

Retrying SubmitTransaction() is safe on Stellar: each envelope is uniquely keyed by transaction hash plus source-account sequence number, so a resubmit either returns the cached server result or fails with tx_bad_seq — there is no double-spend window. If your tx had already committed when the transient failure occurred, the retry surfaces tx_bad_seq and your code should look up the transaction by its hash to recover the original result.

Scope: this preset is for Server (Horizon) only. Do NOT wire it into SEP service clients (ClientWebAuth, InteractiveService, TransferServerService, KycService): SEP-10 POST /auth consumes a one-shot challenge, SEP-24 POST /transactions/{deposit,withdraw}/interactive creates a fresh transaction row per call, SEP-12 POST /customer/files stores a fresh file per call, and SEP-6 PATCH /transactions/{id} is not in the official spec. For SEP clients, use WithConnectionRetries() (mind its all-methods connection-retry caveat) or build a custom HttpResilienceOptions whose RetryHttpMethods only contains GET/HEAD/OPTIONS.

For Stellar RPC (Soroban) clients, prefer ForSoroban().

ForSoroban()

Creates options tuned for Stellar RPC (Soroban). Retries connection failures and transient HTTP status codes (408/429/500/502/503/504) on every request — including POST — because Stellar RPC routes every JSON-RPC call (read and write) through HTTP POST and every Stellar operation is idempotent on the wire (queries are pure reads; sendTransaction is keyed by transaction hash plus source-account sequence number, so a resubmit either returns the cached result or fails with tx_bad_seq — no double-spend). Uses a higher retry budget (5 attempts) and longer delays (up to 15s) suited to long-running polling workflows like getTransaction; one-off interactive calls can override MaxRetryCount / MaxDelay for tighter latency.

WithConnectionRetries()

Creates options with connection retries enabled (similar to OkHttp's retryOnConnectionFailure). Retries connection failures (network errors, DNS failures) but not HTTP error status codes.

Connection-failure retries apply to all HTTP methods. A POST whose response was lost (e.g. connection reset after the server processed it) may be re-executed; for strictly one-shot endpoints (such as SEP-10 POST /auth) prefer NoRetry() and recover at the application level instead.
