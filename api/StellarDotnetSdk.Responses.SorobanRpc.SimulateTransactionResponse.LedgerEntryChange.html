Key

The base64-encoded XDR key of the affected ledger entry.

(optional) Stellar RPC tags this field omitempty, so it is absent whenever the key is empty. That is not hypothetical: v23.0.0 and v23.0.1 shipped pre-allocated no-op state changes with no key at all — the same entries whose Type marshalled to "" — fixed in v23.0.2 (stellar/stellar-rpc#506). It is also absent when the entry's key travels in the JSON-XDR keyJson field instead, though this SDK never requests that format.

A missing property does not violate a non-nullable annotation the way an explicit null does, so before this was widened the property advertised a guarantee the wire did not honour and the compiler suppressed exactly the null checks that would have caught it.

Type

The type of ledger entry change: "created", "updated" or "deleted".

Non-nullable, unlike Key: Stellar RPC tags this field neither omitempty nor optional and its MarshalJSON always writes a string, so a conforming server always sends it.

An empty string is possible and is not one of the three documented types: Stellar RPC v23.0.0 and v23.0.1 emitted pre-allocated no-op state changes whose type marshalled to "" (fixed in v23.0.2, stellar/stellar-rpc#506) — the same entries that omitted Key. Compare against the three literals rather than assuming a non-empty value.

Remarks

JsonRequiredAttribute makes "a conforming server always sends it" a contract the deserializer enforces, matching Hash. Without it the non-nullable annotation was unenforced in exactly the direction that matters: RespectNullableAnnotations rejects an explicit null but not an absent property, so an entry with no type left this string holding null and every Type == "created" comparison silently returned false. Requiring it rejects nothing a conforming server sends. Note this enforces presence, not membership: the empty string described above still deserializes.

required carries the same guarantee to the other entry point. The attribute only binds the deserializer, so without it new LedgerEntryChange { Before = "…" } still compiled and still left a non-nullable string holding null — the very state the attribute was added to make unreachable, one entry point over. This matches how the array properties on this type guard both paths, and how Claimant and ClaimableBalanceResponse already declare their always-present fields.
