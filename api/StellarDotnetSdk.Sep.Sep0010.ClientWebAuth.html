Remarks

Typical authentication flow

A typical SEP-0010 authentication flow using this class is:

  1. Create a ClientWebAuth instance. In most cases you should use FromDomainAsync(string, Network, HttpResilienceOptions?, string?, HttpClient?, Dictionary<string, string>?) to load configuration from the anchor's stellar.toml (WEB_AUTH_ENDPOINT, SIGNING_KEY, and network). Use the constructor directly only when you already know all parameters or need custom configuration.
  2. Call BuildChallengeTransactionAsync (or the appropriate method) to fetch or construct a challenge transaction from the SEP-0010 server for the user's Stellar account.
  3. Have the user sign the challenge transaction with their Stellar keypair (typically on-device or in a wallet).
  4. Submit the signed challenge back to the server using the corresponding method on this class. If the server verifies the signatures and validity window, it issues a JWT or other auth token according to SEP-0010.

Choosing between constructor and FromDomainAsync

Use FromDomainAsync(string, Network, HttpResilienceOptions?, string?, HttpClient?, Dictionary<string, string>?) when you have a Stellar home domain (for example, "example.com") and want the SDK to discover the WEB_AUTH_ENDPOINT, SIGNING_KEY, and network passphrase from the domain's stellar.toml. This is the recommended, high-level entry point for most clients.

Use the public constructor when you already know the auth endpoint URL, network, and server signing key (for example, in test environments or when configuration is not coming from stellar.toml), or when you need to inject additional headers or other advanced settings explicitly.

IDisposable and HttpClient ownership

ClientWebAuth implements IDisposable because it may create and own an internal HttpClient instance. When you let ClientWebAuth create its own client (for example, by calling FromDomainAsync(string, Network, HttpResilienceOptions?, string?, HttpClient?, Dictionary<string, string>?) without passing an HttpClient), you should either wrap ClientWebAuth in a using block or explicitly call Dispose() when you are finished with it so the internal client is cleaned up.

If you pass an external HttpClient into the constructor or FromDomainAsync(string, Network, HttpResilienceOptions?, string?, HttpClient?, Dictionary<string, string>?) , that client remains owned by the caller. In that case, disposing ClientWebAuth will not dispose the external client, and you are responsible for managing the HttpClient lifecycle yourself (for example, by reusing a single long-lived instance for performance and resilience).
