AdditionalRetriableExceptionTypes

Additional exception types to retry, in addition to the defaults ( HttpRequestException, TimeoutException, and TaskCanceledException when the request's CancellationToken is not signaled — note that an HttpClient.Timeout cancellation signals that token and is therefore NOT retried). A requested cancellation is never retried or counted as a failure, even when its exception type is registered here — the cancellation check takes precedence.

Scope limitation: This applies only to exceptions thrown from within the HTTP message handler chain (i.e., from HttpClient.SendAsync). It does not apply to exceptions thrown by ResponseHandler after the response is received — including TooManyRequestsException, ServiceUnavailableException, and HttpResponseException. To retry those, use RetryHttpStatusCodes instead — that mechanism inspects the response before it is translated into a typed exception.

Gets whether any resilience feature is enabled (retries, circuit breaker, or timeout). Returns true if MaxRetryCount is greater than 0, EnableCircuitBreaker is true, or RequestTimeout has a value.

MaxRetryAfterDelay

Upper bound applied to a server-provided Retry-After delay (RFC 7231) when RespectRetryAfter is true: a longer Retry-After is capped to this value. Default is 1 minute.

This is intentionally separate from MaxDelay, which bounds the exponential backoff. Servers commonly ask for tens of seconds on HTTP 429 — longer than a typical backoff cap — and honoring that (rather than retrying early against a server that explicitly asked the client to wait) is the whole point of Retry-After. Keep this at or above MaxDelay.

Unlike the backoff/circuit-breaker durations this is not a Polly-bound field (it is applied in the SDK's own delay generator), so its upper bound is RetryAfterParser's representable-delay ceiling (~49.7 days) rather than Polly's 1 day — a larger cap can never bind, since a parsed Retry-After is itself clamped to that ceiling.

RetryHttpMethods

HTTP methods that may be retried on a configured status code. Default: GET, HEAD, OPTIONS — the methods that are safe by RFC 9110. To retry POST (e.g. for Server.SubmitTransaction() on Horizon, or every JSON-RPC call on Stellar RPC), add HttpMethod.Post explicitly. Methods not in this set are never retried on a status code, even if the status code is in RetryHttpStatusCodes.

This is an explicit whitelist by design: future SDK methods that introduce PUT, PATCH, or DELETE are not silently retried unless added here. Some Stellar ecosystem endpoints (e.g. SEP-10 POST /auth, SEP-24 POST /transactions/{deposit,withdraw}/interactive) are explicitly non-idempotent per spec, so a blanket "retry everything" policy is unsafe.

RetryHttpStatusCodes

HTTP status codes that should trigger a retry when received as a response. Default: empty (no status-code retries).
